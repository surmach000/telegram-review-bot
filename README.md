# Telegram-бот для ревью MR

Отдельный локальный проект. Не изменяет шлюз, сервер или их ветки. Подключение Telegram ещё не настроено; постоянно работающей службы пока нет.

## Поведение

| Сообщение коллеги | Действие |
|---|---|
| Одна или несколько ссылок на MR | Поочерёдный запуск тестов и ревью каждого MR: `gpt-6.1-sol`, `high` |
| Ссылка без просьбы | То же ревью |
| Та же ссылка отдельным новым сообщением | Новое ревью актуальной версии |
| Ответ на отчёт с уточнением | Объяснение сохранённого отчёта: та же модель, `medium` |
| `/review` ответом на отчёт | Повторное ревью актуального MR на `high` |
| Уточнение требует нового анализа кода | Переход с пояснения на полное ревью `high` |
| `/status` | Состояние очереди, без обращения к модели |

При недоступности модели более слабая модель не подставляется. Каждый отчёт содержит SHA исходной и базовой версии. Документы фиксируются для каждого ревью с контрольными суммами. Текст замечаний ссылается на пункты требований и строки кода.

По согласованию используется **Git без API**, существующая авторизация текущей учётной записи и явно заданная `base_branch: dev`. Бот скачивает `refs/merge-requests/<номер>/head` и сравнивает с общим предком актуальной `dev`. Настоящая целевая ветка MR автоматически не проверяется; это допущение видно в отчёте. Для MR в другую ветку настройки нужно пересмотреть до ревью. Описание MR и комментарии через API не загружаются.

Принимаются только личные сообщения от одного разрешённого числового Telegram ID. По умолчанию разрешены проекты `gateway`, `server`, `auth-service` на корпоративном GitLab. Остальные ссылки не скачиваются.

## Что установить

- Windows PowerShell 5.1, Python 3.8 или новее, Git, Codex CLI с действующей авторизацией и доступом к `gpt-6.1-sol`.
- Корпоративный VPN, если он требуется для GitLab.
- Работающий Docker Desktop в режиме Linux-контейнеров — для тестов MR.
- Доступ к локальным документам ЭДО, перечисленным в `config.example.json`.

Отдельные Python-библиотеки не нужны. Проверено на Windows / Python 3.8 и Linux / Python 3.12.

## Первое подключение

1. Откройте [BotFather](https://t.me/BotFather), отправьте `/newbot`, задайте название и уникальное имя. Создаётся отдельный бот; доступ к личной переписке пользователя ему не нужен.
2. Проверьте, что под этой учётной записью Windows уже работает скачивание корпоративных репозиториев через Git. Дополнительный GitLab-токен не требуется. Все проверяемые MR должны предназначаться для `dev`.
3. В PowerShell перейдите в эту папку и запустите:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\setup-windows.ps1
   ```

4. Введите **только токен Telegram-бота** в скрытом запросе этого окна. В чат его отправлять не нужно. Скрипт сохраняет его через Windows DPAPI в `telegram-token.clixml`. Расшифровка привязана к текущей учётной записи Windows и компьютеру. Git продолжает пользоваться своим хранилищем учётных данных; бот их не копирует.
5. Во время настройки попросите коллегу отправить `/start` новому боту. Продолжите настройку: скрипт покажет числовые ID личных отправителей. Укажите подтверждённый ID нужного коллеги. Имя пользователя не используется как средство авторизации.
6. Создастся `config.local.json`, подготовятся текстовые снимки документов. Скрипт ничего не запускает в фоне.
7. Запустите бота:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\start-windows.ps1
   ```

Коллега может повторно отправить `/start`, затем ссылку на MR. Начальное сообщение `/start`, присланное до завершения настройки, может быть пропущено: обработка рабочих запросов начинается с момента настройки.

Если ID нужно определить отдельно после сохранения токена:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start-windows.ps1 -Action discover
```

Эта команда только показывает ID отправителей из ожидающих обновлений. Перед её выполнением работающий бот нужно остановить.

## Проверка после подключения

1. От разрешённого коллеги отправить одну ссылку: появятся номер задания и отчёт с `high`, HEAD и BASE.
2. Отправить две ссылки одним сообщением: первый отчёт придёт до начала следующего ревью.
3. Ответить на отчёт «Объясни первое замечание»: придёт пояснение с `medium`.
4. Ответить `/review`: начнётся новое ревью на `high`.
5. Повторно прислать ту же ссылку новым сообщением: создастся новое задание.
6. Написать от другой учётной записи: ответа и задания не будет.
7. Перезапустить процесс: завершённые ревью повторно не выполняются, очередь сохраняется.

## Остановка и файлы

`Ctrl+C` прекращает приём; текущий запрос Codex завершается перед остановкой процесса. Окно сообщит об ожидании. Не запускайте второй экземпляр до завершения первого. Файловая блокировка не допускает два процесса на одном каталоге данных.

- `runtime/queue.sqlite3` — очередь, полученные update ID, отчёты и статусы доставки.
- `runtime/jobs/<номер>/` — закреплённые исходники, diff, метаданные MR, документы и ответ Codex.
- `documentation/` — подготовленные документы; используются только файлы из `manifest.json`.
- `config.local.json` — разрешённый пользователь, проекты и локальные пути.
- `telegram-token.clixml` — зашифрованный токен Telegram. Не передавайте его вместе с проектом. Возможный `gitlab-token.clixml` из раннего варианта подготовки больше не используется.

Исходники и отчёты корпоративные: храните каталог проекта под своей учётной записью, ограничьте к нему доступ средствами ОС. Автоматическое удаление истории пока не реализовано.

## Сбой отправки в Telegram

Если неизвестно, принял ли Telegram сообщение, автоматического повтора нет: очередь приостанавливается. Уже выполненное ревью заново не запускается. Остановите бота и посмотрите состояние:

```powershell
.\start-windows.ps1 -Action queue
.\start-windows.ps1 -Action deliveries
```

Если сообщение не пришло, явно разрешите повтор конкретной доставки:

```powershell
.\start-windows.ps1 -Action retry-delivery -DeliveryId 7
```

Такой ручной повтор может продублировать сообщение, если прежняя отправка всё же состоялась. Если сообщение уже есть и известен его реальный Telegram message ID, подтвердите существующую доставку:

```powershell
.\start-windows.ps1 -Action ack-delivery -DeliveryId 7 -MessageId 123
```

Затем снова запустите бота. Номера в примере условные.

## Ожидание корпоративного VPN и GitLab

Если перед скачиванием MR GitLab недоступен либо соединение оборвалось при скачивании, задание переходит в `waiting_for_gitlab`. Бот один раз отвечает на исходное сообщение точным текстом:

> Задание принято. Ожидаю доступности GitLab и включения корпоративного VPN

Повторы происходят через 30, 60, 120 секунд, затем каждые 300 секунд без срока автоматического отказа. Счётчик попыток, время следующего запуска и факт отправки уведомления сохраняются в SQLite и переживают перезапуск. Первое ожидающее задание удерживает порядок очереди; последующие MR не обгоняют его. `/status` показывает ожидание, безопасную причину и время до следующей попытки.

Проверяется реальный доступ через Git, а не наличие процесса VPN. Отдельно выполняется короткая проверка доступности нужной ветки; ошибка во время самого `fetch` также сохраняет задание для повтора. Временные сетевые ошибки и тайм-ауты повторяются; неверные права/учётные данные, отсутствующая ветка и недоверенный TLS-сертификат требуют исправления и не маскируются ожиданием VPN.

После успешной подготовки снимок MR закрепляется в `mr.json`. Уже подготовленные исходники и сохранённый результат тестов повторно не скачиваются и не запускаются из-за ожидания сети. Если скачивание не завершилось, очищаются только промежуточные файлы подготовки этого задания. Если вопрос уже был переведён с medium на high, этот факт тоже сохраняется: повторная попытка не оплачивает новое пояснение на medium.

Если при запуске недоступен Telegram, процесс ждёт и повторяет подключение через 5, 10, 30, затем каждые 60 секунд. Отдельный механизм отправки сообщений сохраняет прежнее правило: неоднозначная доставка не повторяется без ручного решения. Автозапуск процесса после включения Windows по-прежнему не настроен.

Локальная проверка обрыва и восстановления без отправки сообщений: `python .\verify-network-wait.py`. Она использует отдельную временную очередь, имитирует недоступность Git через неработающий локальный прокси, затем проверяет скачивание через обычное соединение. Настройки VPN и системного прокси не изменяются.

## Обновление требований

Измените `documentation_sources` в `config.local.json`, остановите бота и выполните:

```powershell
.\start-windows.ps1 -Action prepare-docs
```

Новые задания получат обновлённые документы. Снимки уже выполненных ревью сохраняются. Внешние ссылки и Kaiten автоматически не читаются; нужные утверждённые требования следует добавить в список локальных источников. Поддерживаются DOCX, Markdown и UTF-8 TXT. Для DOCX извлекается текст основного документа и таблиц; изображения, комментарии и вложения не анализируются.

## Контекст рабочего чата

Кроме требований ревью получает отобранные обсуждения из чата: `D:\eldoc-README\docs\telegram-review-context.md`. В нём разделены подтверждённые решения, исторические примеры, открытые и отложенные вопросы, личный порядок проверок и типичные ошибки. Отдельно подключены точные исходные методологии Java-тестов и JavaDoc из `review_context_sources`.

В начале нового задания эти UTF-8 файлы копируются в `runtime/jobs/<номер>/review-context/`. `manifest.json` содержит источник, время и SHA-256 каждого файла; общий digest указывается в отчёте. Перезапуск/ожидание VPN не обновляет уже зафиксированную версию. При уточняющем вопросе доступны текущие договорённости и снимок исходного отчёта в `previous-review-context/`, если он существовал.

Уточнение 21.11.2026: Telegram-ревьюер не оценивает оформление кода/тестов, JavaDoc, импорты, порядок объявлений, имена тестов, DisplayName и разметку Given/When/Then. Коллега проверяет это отдельно. Смысл тестов, покрытие сценариев, переносимость и корректность проверяются. Сохранённая методология остаётся историческим контекстом, а не основанием для стилистических замечаний. Личный workflow подготовки изменений пользователя этим не отменяется.

Чтобы новое согласованное решение дошло до следующих ревью, нужно записать его в файл контекста. Рабочие инструкции текущего чата дополнены этим правилом. **Бот не читает живую историю Codex и не получает будущие сообщения автоматически**; он автоматически читает обновлённый файл при новом задании, без перезапуска и без `prepare-docs`. Не включайте туда реквизиты и личную переписку. Явный список источников ограничивает чтение; обнаружение известных форматов токенов дополнительно останавливает создание снимка, но не заменяет проверку содержимого человеком.

Если обязательный источник недоступен или готовый снимок изменён, ревью завершается безопасной ошибкой вместо молчаливого запуска без рабочего контекста. Тестовый контейнер получает только `head`, поэтому контекст чата в исполняемый код MR не передаётся. Контекст не разрешает ревьюеру выполнять действия, запрещённые основным заданием.

## Проверки проекта

```powershell
python -m unittest discover -s tests -v
python .\verify-codex.py
python .\verify-git.py
python .\prepare-test-cache.py
python .\verify-test-runner.py auth-service
docker build -f Dockerfile.tests -t telegram-review-bot-tests:local .
docker run --rm --network none telegram-review-bot-tests:local
```

`verify-codex.py` делает один короткий настоящий запрос на `6.1 Sol/high` с чтением контрольного файла. Каждый рабочий запрос тоже требует правильного содержимого случайного контрольного файла: если чтение заблокировано, успешное ревью не объявляется. На Windows явно выбирается штатный механизм `windows.sandbox=elevated`, режим остаётся `read-only`; автоматического отключения защиты нет. Остальные тесты не обращаются в Telegram, GitLab или модель. Тестовая сборка Docker не включает настройки, токены и историю.

`verify-git.py` отдельно обращается к GitLab через Git: проверяет доступ к `dev` трёх проектов и скачивает MR !13 шлюза во временный каталог. Не вызывает API, модель или Telegram; не изменяет ветки и удаляет временные файлы. Старые `check-gitlab*` и `check-existing-gitlab.py` остаются отдельными утилитами диагностики API, в штатном запуске не участвуют.

## Автоматические тесты MR

После скачивания закреплённого HEAD бот запускает тесты, затем передаёт результаты ревьюеру:

- Шлюз: Linux / Java 17 / Maven 3.9.9, `mvn -B -ntp -U clean install` с отдельным локальным Maven-репозиторием.
- Auth-service: та же версия среды, полный `clean install -U`, затем `-Pintegration-test failsafe:integration-test failsafe:verify`.
- Сервер: Java 17 / Maven 3.9.6 по проверенному CI, те же два прогона.
- Для server/auth-service создаются одноразовые PostgreSQL 16 и Valkey 8. Интеграционные тесты получают только адреса и тестовые реквизиты этих сервисов.

Настоящие Windows-тесты и CryptoPro `native-it` этим runner **не выполняются**. Они требуют отдельной подходящей среды, а для CryptoPro — ещё провайдера и тестового контейнера ключа. Это явно указано в отчёте; обычные пропуски JUnit тоже учитываются.

Код выполняется от UID 10001 в отдельном контейнере: без токенов, хоста Docker, привилегий, опубликованных портов и прямого доступа в интернет. Исходный снимок MR остаётся неизменным; тесты получают его отдельную копию на внутренней ФС Docker. Для каждого задания выделяются новые том и внутренняя сеть, которые удаляются после выполнения или тайм-аута. Java получает отдельный записываемый домашний каталог, а имя контейнера разрешается локально.

Зависимости предварительно копируются в `runtime/maven-artifacts` из локального Maven-кэша: только JAR/POM, без `settings.xml`, учётных данных и SNAPSHOT-артефактов. Внутри задания создаётся отдельная копия кэша, поэтому MR не изменяет зависимости следующих заданий. Недостающие публичные артефакты Maven получает через отдельный контейнер-загрузчик: он разрешает только GET/HEAD стандартных Maven-файлов с единственного адреса `https://repo.maven.apache.org/maven2/`, не пересылает авторизацию и запрещает перенаправления. Настройки Maven принудительно используют этот адрес через внутреннее зеркало. Сам код тестов выхода в интернет не получает.

Если нужна отсутствующая приватная зависимость, сборка остановится; бот сообщит об этом, а не объявит тесты пройденными. Для пополнения такого кэша используйте артефакты доверенной сборки и повторите `prepare-test-cache.py`; не запускайте неизвестный MR на хосте ради заполнения кэша.

В `test-results/` сохраняются журнал Maven и `summary.json`. Ревьюер читает фактические счётчики Surefire/Failsafe и имена упавших тестов. Падение unit-тестов не мешает отдельной попытке запуска IT, если компиляция и зависимости позволяют это сделать. Наличие Maven exit code 0 без тестовых отчётов не считается успешным прогоном.

Это изоляция Docker для рабочего тестового стенда, а не полноценная VM для намеренно враждебного кода. Для внешних недоверенных авторов лучше выделить отдельную машину/VM.

## Границы работы

Бот работает, пока запущен процесс и компьютер имеет доступ к Telegram, GitLab и Codex. После сна или выключения работа возобновится при запуске. Telegram хранит необработанные обновления не более 24 часов; это ограничение не устраняет локальная очередь.

При фоновом запуске остановить приём новых заданий можно командой `python -m reviewbot stop`. Процесс дождётся текущего задания и завершится; затем его можно снова запустить через `start-windows.ps1`.

Нет автоматических коммитов, push, merge, деплоев, комментариев в GitLab или чтения других Telegram-чатов. Пересылка отчёта происходит только в разрешённый личный чат бота.

Справка: [Telegram Bot API](https://core.telegram.org/bots/api#getupdates), [неинтерактивный Codex](https://learn.chatgpt.com/docs/non-interactive-mode), [изоляция Codex на Windows](https://learn.chatgpt.com/docs/windows/windows-sandbox).
